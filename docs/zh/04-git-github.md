# 04 Git 与 GitHub

版本控制是你给智能体系的安全绳,出了问题一条命令就能退回去。

## 节奏

1. 开始前确认工作区干净(`git status`)
2. 一个任务一个分支
3. 小步改动,自己看 `git diff`
4. 满意再提交,信息写清楚;可以让智能体写,**diff 必须自己过**
5. 通过 Pull Request 合并,哪怕只有你一个人

提交一次只做一件事;重构、功能、大范围格式化分开提交。

## 每个项目维护 CHANGELOG.md

记录**功能迭代和 bug 修复**,按日期组织,同一天的改动合并记录。它既是你的回顾材料,也是智能体和同事快速了解项目演进的入口。

```markdown
## 2026-11-25
### 新增
- 配体清洗脚本 `scripts/clean_ligands.py`
### 修复
- 修复非法 SMILES 导致的崩溃
```

可以让智能体在每次完成任务后顺手更新,你来核对。模板:[`templates/CHANGELOG.md`](../../templates/CHANGELOG.md)。本仓库的 [CHANGELOG](../../CHANGELOG.md) 就是这个格式。

## 什么不该进仓库

| 类型 | 做法 |
|---|---|
| 密钥、令牌 | 放环境变量,绝不提交;误提交后立刻作废更换 |
| 大数据、模型权重 | Git LFS、DVC 或外部存储,仓库里只放获取方式 |
| 未发表的结构、受试者数据 | 默认不上传,见 [05](05-verify-and-safety.md) |
| 可再生的中间结果 | 加入 `.gitignore`([模板](../../templates/gitignore)) |

## 打标签

论文或报告用到的那一版分析打一个 tag(如 `v1.0-paper`),并在文档里写明对应的数据版本和环境。

智能体改了你没预期的文件,先别提交,问它为什么,必要时 `git restore`。公开仓库提交前,再检查有没有混入路径、邮箱、内部数据。
