# 08 项目的生长与审美

这一章不讲具体操作,讲我们对"好项目"的看法。

## 好东西是长出来的

好的项目、好的 skill、好的代码、好的文档,都不是一开始设计出来的,而是**随着你对项目理解的加深,一点点长出来的**。

- 第一天,你对问题的理解是浅的,写出的东西也是粗糙的。
- 做的过程中,你发现哪些步骤总是重复、哪些地方总是出错、哪些约定值得写下来。
- 把这些发现沉淀下来:变成函数、变成测试、变成 `AGENTS.md` 里的一条规则、变成一个 skill。

所以**不要一开始就搭一个庞大的框架**。先做起来,在真实的痛点上生长。

## 两个层次

| 层次 | 内容 | 例子 |
|---|---|---|
| **项目内** | 只属于这个项目的理解 | 这个数据集的坑、这套流程的约定、专属的 skill |
| **跨项目** | 跨项目通用的经验,也就是我们说的"风格" | 目录习惯、命名习惯、提交习惯、对智能体的使用习惯 |

两者像画的两个维度:项目内的理解决定它**对不对**,跨项目的风格决定它**美不美**。
跨项目的经验可以放进你个人的全局说明(Codex 支持用户级的 `AGENTS.md`,位置见官方文档),
这样每个新项目都从你的风格出发。

## 简洁就是美

项目的优雅,一方面在于**用精简的实现完成功能**。

另一方面,好的项目会妥善处理一些基础但重要的概念:

- 多线程 / 并行
- 缓存机制
- 代码的分类与模块划分
- 工具的命令行(CLI)与 API 接口
- 解耦合

但关键不在于"都用上",而在于**在哪个关键点用、什么时机用、什么时候可以直接跳过**。
过早的并行、不必要的缓存、只用一次的 CLI、为解耦而解耦,都是在给未来的自己添麻烦。

判断时可以问自己几个问题:

- 这个优化带来的收益,我量过吗?
- 这个东西会被重复使用吗?还是只用这一次?
- 加上这层抽象,代价比收益大吗?
- 删掉它,项目会变差吗?

这些判断没有标准答案,需要在项目里反复打磨。

## 建立自己的审美

这一点很关键。智能体能写出"能跑"的代码,但"好不好看"取决于你的审美。

- 看到一段代码,觉得哪里别扭,说出来,并让智能体改。
- 定期让它帮你**修剪**:"有没有可以删掉的代码?哪里重复了?哪里过度设计了?"
- 把你认可的写法记进 `AGENTS.md`,让它下次直接照着做。
- 多读好项目的代码和文档,积累判断力。

没有审美,智能体会产出平均水平的东西。有了审美,它会成为你风格的放大器。

## 小结

- 好东西是长出来的,在真实的问题里生长。
- 项目内的理解与跨项目的风格,共同构成项目的美。
- 简洁是目标;关键点用,其余可以跳过。
- 审美需要自己建立,这是智能体替代不了的部分。
