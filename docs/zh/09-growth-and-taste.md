# 09 项目的生长与审美

这一章不讲操作,讲我们对"好项目"的看法。

## 好东西是长出来的

好的项目、skill、代码和文档,不是一开始设计出来的,而是随着你对项目理解的加深一点点长出来的:

- 第一天理解浅,写出的东西粗糙
- 做的过程中,你发现哪些步骤总在重复、哪里总出错、哪些约定值得写下来
- 把发现沉淀下来:函数、测试、`AGENTS.md` 里的一条规则、一个 skill

所以别一开始就搭庞大的框架,先做起来,在真实的痛点上生长。

## 两个层次

| 层次 | 内容 |
|---|---|
| 项目内 | 只属于这个项目的理解:数据的坑、流程约定、专属 skill |
| 跨项目 | 通用的经验,即"风格":目录、命名、提交、与智能体相处的习惯 |

项目内的理解决定它**对不对**,跨项目的风格决定它**美不美**。
跨项目的经验可以放进用户级的全局 `AGENTS.md`(位置见官方文档),让每个新项目从你的风格出发。

## 简洁就是美

优雅的项目,一方面用精简的实现完成功能;另一方面,妥善处理一些基础概念:
多线程与并行、缓存、代码分类与模块划分、CLI 与 API 接口、解耦合。

关键不在"都用上",而在**哪个点用、什么时机用、什么时候直接跳过**。
过早的并行、不必要的缓存、只用一次的 CLI、为解耦而解耦,都是在给未来的自己添麻烦。可以问自己:

- 这个优化的收益,我量过吗?
- 它会被重复使用吗?
- 加这层抽象,代价比收益大吗?
- 删掉它,项目会变差吗?

没有标准答案,需要在项目里反复打磨。

## 自己造轮子

我们**不推荐**使用 GPT-Rosalind 和 Codex 的 Life Sciences 插件这类高度封装的方案:封装太多,你看不到里面发生了什么,也学不到东西。

我们更喜欢自己造轮子。在 agent 时代,造轮子比过去便捷得多,而且过程中你会学到很多。
自己写的工具你清楚它的边界,出了问题知道往哪里查,这也是审美的一部分。

## 建立自己的审美

智能体能写出"能跑"的代码,"好不好看"取决于你的审美。

- 觉得哪里别扭,说出来,让它改
- 定期让它帮你**修剪**:哪些可以删、哪里重复、哪里过度设计
- 把认可的写法记进 `AGENTS.md`
- 多读好项目的代码和文档

没有审美,智能体产出的是平均水平;有了审美,它是你风格的放大器。
